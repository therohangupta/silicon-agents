# Agent Fleet Services

Directory-level map of every first-party process under `services/`.
Each sibling folder is a deployable unit (or a shared base image). This README
summarizes roles, ports, and how services connect; open each service’s own
`README.md` for API and module-level detail.

## Compose layout

Two Docker Compose projects split **platform** from **agent runtimes**:

| Project | File | What runs |
|---------|------|-----------|
| Platform | `docker-compose.yml` (+ rendered `docker-compose.platform.generated.yml`) | Postgres, NATS, fleet-server, telemetry, storage-writer, gateway, memory-plane stores |
| Silicon agents | `docker-compose.agents.yml` (generated by `scripts/startup.sh`) | One container per selected agent, all built from `silicon_agent` |

The platform stack exposes **`agent_fleet`** as an external network so agent
containers can reach `telemetry`, `nats`, and `db` by service name. The
dashboard (`dashboard-web/`) is developed separately and points at the gateway
on port **8000** by default.

## Data and control flow (high level)

```
Operators / dashboard / SDK
         │
         ▼
    gateway (HTTP/WS :8000) ──gRPC──► fleet-server (:50051)
         │                                    │
         │ TELEMETRY_URL                      │ plans, tasks, agent registry
         ▼                                    ▼
    telemetry (:9000 HTTP, :9001 gRPC)   agent containers (silicon_agent image)
         │                                    │
         │ publish telemetry.>                │ heartbeats, StreamTelemetry
         ▼                                    │
       NATS JetStream ◄───────────────────────┘
         │
         ├──► gateway (optional live fan-out to browsers)
         └──► storage-writer (persist=true → Parquet)
```

Heartbeats and rich telemetry take **different paths** on purpose: heartbeats
stay in telemetry’s in-memory store and health APIs; validated protobuf events
ride JetStream for durability and live UI streams.

## Telemetry vs gateway

These names are easy to conflate because both touch “telemetry” in the product.
They are separate processes with distinct contracts.

| Concern | **Telemetry** (`services/telemetry/`) | **Gateway** (`services/gateway/`) |
|---------|----------------------------------------|-----------------------------------|
| Primary clients | Agent task servers (heartbeats, gRPC/HTTP ingest, blob upload) | Dashboard, CLI HTTP clients, browser WebSockets |
| Control plane | None — does not talk to fleet-server for business logic | gRPC bridge to fleet-server for goals, plans, tasks, registration |
| Agent liveness | **Source of truth**: ring buffers, derived reachable/busy, timeout scanner | **Proxy**: `TelemetryClient` calls `GET /health/*` on telemetry |
| Event stream | **Publisher**: validates, dedupes, stamps `ingest_time_ns`, publishes to `telemetry.{modality}.{agent_id}` | **Consumer** (optional): subscribes to `telemetry.>` for live UI; posts internal events from other services |
| Health fan-out | Pushes `telemetry.health_changed` to gateway `GATEWAY_EVENT_URL` when effective reachability flips | Receives internal events and invalidates WebSocket subscribers |
| Blobs | **Write path**: `POST /telemetry/blob` → local disk or S3 | **Read path**: serves or proxies blob URIs for the dashboard |
| Durable analytics | Does not write Parquet | Does not write Parquet |

Rule of thumb: **agents talk to telemetry for observability; humans and tools
talk to the gateway for fleet operations.** The gateway never replaces telemetry
for heartbeat storage — it only reads summaries and forwards UI-facing traffic.

## fleet_server

gRPC **Fleet Manager** control plane. Owns goals, plans, tasks, and agent
registration; runs planners (monolithic / DAG / big DAG / replanner) and
allocators (LP / LLM / cost-based); executes plans and emits mutation events
toward the gateway. Container entrypoint: `python -m services.fleet_server.src`
on port **50051**.

Documentation for planners, allocators, and executors lives under
`fleet_server/` (maintained separately).

## gateway

HTTP/WebSocket **edge API** in front of the fleet. Exposes REST under `/api` for
the dashboard and HTTP consumers, bridges to fleet-server over gRPC, scans agent
YAML embodiments, consumes health/invalidation events, and fans updates to
connected UI clients. Proxies agent health from telemetry and blob reads from
shared storage roots. Typical local port **8000**.

See [`gateway/README.md`](gateway/README.md) for router layout and env vars.

## telemetry

Specialized **ingest and health** service for agent runtimes:

- Heartbeats → in-memory `HeartbeatStore` (identity `host:port`, latest-wins coalescing).
- Health read API for the gateway (`GET /health/summary`, `GET /health/{agent_id}`).
- Push `telemetry.health_changed` to the gateway when reachability changes (heartbeat or timeout scanner).
- HTTP and gRPC telemetry ingest → NATS JetStream subject `telemetry.>`.
- Vision blob upload (bytes off the bus; URIs on the bus).

If NATS is down, **heartbeat-only mode** still works; telemetry ingest fails
until the bus reconnects. HTTP port **9000**; gRPC on `TELEMETRY_GRPC_PORT`
(often **9001** in Compose).

See [`telemetry/README.md`](telemetry/README.md) for API tables and configuration.

## storage_writer

**Durable sink** for the telemetry event bus — not an API service. Pulls
`telemetry.>` as durable consumer `storage-writers` (queue group for horizontal
scale), acks messages, and writes only events whose protobuf `tags["persist"]`
equals `"true"`. Buffers rows into modality-specific Snappy Parquet under
Hive-style partitions, flushes on row/time thresholds, writes `_manifest.json`
sidecars (footer metadata only), and runs a background compaction loop (~128 MB
target files, sorted by `step_index`, `sequence_id`).

Started with `python -m services.storage_writer.src.main`. Shares
`PARQUET_STORAGE_ROOT` / bind mounts with telemetry and gateway under
`.data/telemetry` in local Compose.

See [`storage_writer/README.md`](storage_writer/README.md) for partition layout
and operational notes.

## dashboard-web

Vite + React + TypeScript operator UI (`agent-fleet-dashboard`). Talks to the
gateway over HTTP/WebSocket; uses `@agent-fleet/client-sdk`, React Query,
React Flow, and Tailwind. Documented in `dashboard-web/` (maintained separately).

## cli

Placeholder directory for a **future service-packaged CLI image**. It contains
no application source today — only this README.

The interactive operator CLI is the Python package at [`../cli/`](../cli/)
(`agentctl`, Click + `FleetManagerClient` gRPC). That CLI runs on the host (or
any environment with the editable install) and does **not** require this folder.

Reserve `services/cli/` so Compose can eventually ship a slim container (for
example `agentctl` preinstalled, `GATEWAY_URL` baked in, no local Python) without
renaming images or colliding with the `agent_fleet.cli` import path.

See [`cli/README.md`](cli/README.md) for the intended split and migration notes.

## silicon_agent

Shared **base Docker image** for silicon/EDA agent containers (`python:3.11-slim`,
editable install of the full `agent_fleet` tree, `PYTHONPATH=/app`). Compose
builds once as `agentfleet/silicon-agent:dev`, then sets each service’s
`working_dir` to a specific `agents/<track>/…/<name>` package and runs
`python server.py`. No default `CMD` in the Dockerfile — the agent package
defines the process.

Individual agents add their own `Dockerfile` only when they need extra system
packages or non-Python dependencies; most reuse this image.

See [`silicon_agent/README.md`](silicon_agent/README.md) for build context,
environment variables injected by `docker-compose.agents.yml`, and override
patterns.

## Shared configuration

Most services re-export knobs from `packages.config` (loaded from
`config/platform.yaml` and the repository `.env`). Common cross-service variables:

| Variable | Typical consumers |
|----------|---------------------|
| `NATS_URL` | telemetry, storage-writer, gateway, agents |
| `GATEWAY_EVENT_URL` | fleet-server, telemetry (health-changed POST target) |
| `TELEMETRY_URL` | gateway, agents (HTTP health / ingest) |
| `BLOB_STORAGE_ROOT` / S3 settings | telemetry (write), gateway (read) |
| `PARQUET_STORAGE_ROOT` | storage-writer |

## Local development shortcuts

From `` after `pip install -e .`:

```bash
# Platform stack (includes telemetry + storage-writer + gateway)
docker compose up --build

# Agent containers (after platform network exists)
docker compose -f docker-compose.agents.yml up --build
```

Bare-metal telemetry or storage-writer:

```bash
python -m services.telemetry.src --port 9000
python -m services.storage_writer.src.main
```
